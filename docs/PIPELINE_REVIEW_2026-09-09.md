### C1 · P1 — 400개 응답의 마지막 가격과 같은 매물을 소진으로 오판

- 위치: `src/collect.ts:147–156`.

- 실제 collectItem 코드를 VM에서 실행하고 API·DB를 가짜 응답으로 대체했다. 동일 가격 400개를 반환하고 그 가격의 기존 매물 140개를 응답 밖에 두자, 소진량 140개가 잘못 생성됐다.

- 수정: 응답이 잘렸을 때 경계 가격과 같은 미관측 매물도 판정을 보류한다. 재관측 사례에 대한 기존 잘못된 소진 기록의 처리 기준도 정한다.

## 2. DB 집계·보존

### D1 · P1 — 매시 2분 집계가 48시간 전 시간봉의 앞부분을 잘라 덮어씀

- 위치: `sql/schema.postgres.sql:86`, `sql/scheduler.sql:77`.
- cron은 `refresh_candles_1h(now() - interval '48 hours')`를 매시 2분에 호출한다. 함수는 sold_date를 그 시각부터 필터링하면서 결과는 정시 기준 시간봉 전체에 upsert한다.
- 예: 9월 8일 21:02 KST 실행은 9월 6일 21:00~21:02의 체결을 제외한 값으로 21시 봉을 덮어쓴다. 다음 실행에서는 이 봉이 조회 범위 밖으로 빠져 자동 복구되지 않는다.
- 운영 DB에서 최근 미집계 구간과 원본 보존 경계의 불완전한 첫 시간은 비교에서 제외했다. 23:59경 불일치 24봉, 다음 정기 집계 뒤 00:02경 **33봉**이었다. 33봉 중 비카드 20봉이며, 전체 차이는 체결 건수 63건·수량 191개였다. 원본에는 남아 있으므로 복구할 수 있다.
- 실제 예: `+11 장비 증폭권[골고라이언]`의 9월 6일 21시 봉은 원본 5건, 저장 봉 4건. 빠진 21:00:24 체결은 집계보다 하루 이상 앞서 이미 적재돼 있었다.
- 운영 함수 본문을 임시 테이블용으로 복제해 재현했다. 12:00:24 가격 100, 12:05:14 가격 200을 처음 집계하면 2건·VWAP 150이다. 시작값을 12:02로 바꿔 재집계하니 1건·VWAP 200으로 훼손됐다. 테스트는 롤백했다.
- 수정: 함수 내부에서 조회 하한을 `date_trunc('hour', p_from)`으로 정렬한다. 원본이 온전히 남아 있는 시간봉을 복구하고, 오래된 원본이 이미 잘린 경계 시간은 별도로 취급한다.
- 검증: 분·초가 있는 p_from으로 반복 실행해도 봉의 OHLC·VWAP·수량·건수가 유지돼야 한다. 복구 후 운영 원본과 읽기 전용 대조에서 불일치 0을 확인한다.

### D2 · P1 — 48시간보다 오래된 백필의 집계 보장과 삭제 전 검증이 없음

- 위치: `sql/scheduler.sql:73–86`, `src/collect.ts:163–170`.
- 수집기는 과거 체결을 넣지만 정기 집계는 sold_date 기준 최근 48시간만 읽는다. 이후 새 종목을 백필하면 그보다 오래된 체결은 정기 집계에 들어가지 않는다.
- 원본 삭제는 `sold_date < now() - interval '30 days'`만 검사한다. 문서에 적힌 “시간봉으로 집계된 원본만 정리” 조건은 실제 운영 SQL에 없다.
- 임시 테이블 재현에서 오래된 백필은 원본에 있어도 시간봉 0개였다. 운영 원본 중 적재 지연이 48시간을 넘는 체결은 2,064건이었다. 다만 **현재 조회한 삭제 후보 5건은 모두 대응 시간봉이 있었고, 미집계 상태로 영구 삭제된 실제 사례까지 확인한 것은 아니다.**
- 수정: 새로 들어온 체결의 영향 시간봉을 재집계하거나 집계 완료 지점을 관리한다. 삭제는 해당 구간 집계의 완전성을 확인한 뒤 같은 처리 단위에서 수행한다. 단순히 대응 봉이 존재한다는 조건만으로는 늦게 추가된 체결의 반영을 보장하지 못한다.
- 검증: 3일·29일 전 백필, 집계 실패, 원본 삭제 경계가 시간 중간인 경우를 격리해서 확인한다. 집계 실패 시 원본이 남아야 한다.

## 3. 스케줄러·감시

### S1 · P1 — 일부 아이템만 멈추면 알림·복구로 이어지지 않음

- 위치: `sql/watchdog.sql:63–71`, `scripts/health.ts`.
- 전역 마지막 성공이 20분 이내면 stale_items가 있어도 기록 후 RETURN한다. CLI health 역시 전역 마지막 성공 하나만 검사한다.
- 따라서 hot 그룹만 정상이고 rest 그룹이 멈추는 등 부분 장애는 다른 아이템의 성공에 가려질 수 있다.
- 운영 watchdog과 파일 본문이 일치함을 확인했다. 함수 복제본에서 정상 아이템 1개·2시간 지연 아이템 1개를 넣자 stale_items=1을 기록하고 외부 요청은 0회였다. HTTP 함수는 임시 기록 함수로 대체했으며 실제 dispatch·Issue 생성은 하지 않았다.
- 수정: 지속되는 개별 아이템·그룹 지연에도 별도 알림 기준을 두고, CLI에도 같은 기준을 반영한다. 재실행만으로 해결되지 않는 반복 API 실패는 원인 확인 대상으로 구분한다.
- 검증: 전역 정상/부분 장애, 전역 장애, 회복, 알림 쿨다운을 각각 재현한다.

### S2 · P2 — 알림이 복구 기록을 덮어써 10분 쿨다운이 깨짐

- 위치: `sql/watchdog.sql:80–100`, `105`, `132`.
- dispatch 후 v_action을 recover로 설정하지만, 이후 alert 또는 alert_cooldown으로 바꾼다. 마지막 INSERT에는 복구를 보낸 사실이 독립적으로 남지 않는다.
- 다음 점검의 쿨다운은 action='recover'만 찾으므로 바로 전 dispatch를 놓친다.
- 실제 함수 복제본에서 과거 복구 2회를 넣고 5분 간격의 점검을 재현하니, 10분 쿨다운 설정에도 dispatch 2회가 발생했다. Issue는 1회였다. 외부 요청은 모두 임시 함수로 대체했다.
- 수정: 복구 시도와 알림 기록/시각을 분리한다. 요청 전송 시도와 HTTP 성공 확인도 구분한다.
- 검증: 알림 발생 전후 모두 dispatch 간격이 최소 10분인지 확인한다.

### S3 · P2 — 수집 실패가 프로세스 성공으로 끝날 수 있음

- 위치: `src/run.ts:103–113`, 시간제한 루프 종료부.
- tick은 오류를 false로 바꾸지만 once 모드는 결과를 버리고 exit(0)한다. 시간제한 모드도 누적 실패를 최종 종료 코드에 반영하지 않는다.
- 실제 run.ts를 VM에서 실행하고 모든 collectItem 호출을 실패시켰다. once 모드는 오류 1건을 출력하고 exit code 0으로 끝났다.
- 수정: 일시적 오류의 재시도는 유지하되, once의 실패 및 시간제한 실행의 지속 실패·미회복 상태를 최종 상태에 반영한다.
- 검증: 전부 실패, 일부 실패, 일시 실패 후 회복을 나눠 종료 코드와 워크플로 결과를 확인한다.

현재 운영 상태는 위 장애 재현과 다르다. 23:58 KST 조회에서 최근 24시간 수집 기록 5,651회 중 기록된 오류 0건, 현재 지연 아이템 0종, 최근 health 기록 283회는 모두 ok였다. cron 9개는 활성 상태였고 보존된 최근 HTTP 응답 30개는 모두 204였다. 이는 현재 기록의 상태이며 미래 장애 경로가 안전하다는 뜻은 아니다. 대기 중 collect 작업이 새 대기 작업으로 교체돼 cancelled로 남은 것은 실행 중 수집 실패와 구분했다.

## 분석 페이지에서 고칠 부분

1. **집계 정합성을 확인한 결과만 새 분석으로 배포한다.** D1·D2를 먼저 고치고 원본이 남은 구간을 복구한 뒤 VR·일봉·예측 평가를 다시 생성한다. 빌드에 읽기 전용 정합성 검사를 넣고 실패하면 잘못된 새 결과를 게시하지 않는다. 화면에는 마지막 검증 시각/상태를 표시한다. 이미 원본이 삭제된 역사 전체를 검증했다고 표현하지 않는다.
2. **최근 7일 소진량 숫자는 정정 전까지 숨기거나 검증 보류로 표시한다.** `web/analysis.html:374–378`은 현재 오류가 섞인 합계를 정상적인 보조 신호처럼 제시한다. 판매·취소 혼재 안내만으로 API 응답 경계의 오판까지 설명되지는 않는다. 정정 뒤에도 체결량과 합산하지 않는 원칙은 유지한다.
3. **빌드 시각과 실제 수집·집계 시각을 구분한다.** `web/analysis.html:265–274`의 “갱신”은 파일 생성 시각이고 “수집 중”은 무조건 출력된다. 마지막 성공 수집 시각, 마지막 성공 집계 시각, 종목별 지연 여부를 별도로 연결한다. 파일만 새로 구워도 수집이 정상처럼 보이지 않게 한다.
4. **빈 시간봉의 의미를 보완한다.** 무거래와 수집 실패·미집계를 같은 “연속 관측 부족”으로만 설명하지 않도록, 확인 가능한 수집 상태와 함께 안내한다. 7일을 넘겨 삭제한 수집 실행 로그로는 과거 전체 공백 원인을 소급 확정할 수 없으므로 모르는 구간은 원인 미상으로 남긴다.

영향을 가늠하려고 00:02경의 불일치 봉만 메모리에서 원본 값으로 바꾸어 같은 VR 코드를 다시 실행했다. 검정 가능 11종·유의한 반전 1종은 유지됐다. VR 중앙값은 0.70315994 → 0.70286972로 달라졌다. **현재 표본에서는 큰 결론이 뒤집히지 않았지만, 수치와 입력 데이터에 실제 수정이 필요하다.** 이 계산은 운영 DB 복구나 전체 분석 재검증을 대신하지 않는다.

권장 실행 순서: **D1·D2 집계/보존 → 원본 대조 및 복구 → C1 소진 판정/기존 기록 정정 → S1~S3 감시 → 분석 재빌드와 상태 표시**. D3 테스트 분리는 집계 수정과 함께 진행한다.
