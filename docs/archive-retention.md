# 원본 보존과 저장 사용량 측정

운영 B/C의 `listing_snapshots`는 최근 14일 이상, `listings`는 종료·예정 만료 시각이
모두 14일보다 오래된 행을 정리 후보로 삼는다. 기준은 검증한 보관본의 UTC 시각에서
14일을 뺀 날의 00:00이므로 실제로는 최소 14일~15일을 보존한다.

매일 R2 보관 작업이 현재 DB 입력의 복원·연구 재현과 전체 과거 자료의 복원을 모두
통과한 뒤에만 정리한다. 별도 pg_cron 삭제 작업은 만들지 않는다.
R2 객체의 SHA-256과 행 원문 해시를 확인하고, 삭제문에서도 현재 행의 해시를 다시 대조한다.
아직 보관하지 못했거나 수정·재개된 행은 남긴다. 카드별 최고 강화 단계의 마지막 매물 한 행은
수집기 상태이므로 보존한다. R2 파일 누락·훼손·프로젝트 불일치·사전 읽기 예산 초과면 중단한다.

한 실행의 상한은 R2 압축 파일 20 MB/증명 10만 행이며 삭제는 1천 행씩 처리한다.
행 전체를 Supabase에서 다시 내려받지 않고 정리 건수만 받는다. 각 삭제 묶음은 원자적이다.
중간 실패 때 이미 정리한 묶음은 R2에 보존되어 있고, 재실행은 같은 행을 다시 지우지 않는다.
정리 결과는 실행 artifact `retention.json`과 해당 프로젝트 R2 `retention/`에 기록한다.

전체 과거 자료와 현재 DB는 정리 이후 행 집합이 달라진다. 보관 manifest의 `sourceObject`는
현재 DB 행만 담은 객체를, 기존 `hash`는 정리된 원본까지 포함한 객체를 가리킨다.
따라서 다음 보관 때에도 현재 연구 입력 재현과 전체 과거 복원을 각각 검사할 수 있다.
사이트는 R2의 긴 호가 이력과 현재 DB의 최신 행을 합치므로 카드 차트와 과거 연구 입력을 유지한다.
체결·시간봉·기존 로그 보존 정책과 수집 주기는 이 변경에서 바꾸지 않는다.

보관 보고서의 `usage`에는 측정 시각·프로젝트·DB 크기·테이블별 크기를 매일 기록한다.
DB 크기에는 인덱스와 내부 여유 공간도 포함된다. DELETE 직후 파일 크기가 줄지 않아도
내부 공간은 이후 INSERT에 재사용될 수 있다. 이것은 Supabase 청구 전송량이 아니다.
전송량은 정기 사이트 로그의 소스별 `fetchedBytes`와 조직 Usage를 구분해 측정한다.

초기 측정(2026-09-23 01:10 KST): B 25,193,619바이트, C 18,312,339바이트.
두 DB 모두 14일 초과 후보는 0건이었다. 이 짧은 운영 기간으로 월간 사용량이나
저장 용량이 안정되는 지점을 확정하지 않는다.

Supabase 조직 Usage 조회(2026-09-23 01:22~01:23 KST): B 전송량 0.084/5 GB,
C 0.021/5 GB. 두 조직 모두 한도 초과 없음, 이용 기간 09-22~10-22.
Usage 요약의 DB 크기는 B 0.041/0.5 GB, C 0.034/0.5 GB였다.
이는 위 SQL의 현재 연결 DB 크기와 집계 범위·시각이 다른 대시보드 수치로 별도 기록한다.
화면은 최대 1시간 갱신 지연을 안내하며 정확한 마지막 집계 시각은 표시하지 않았다.
전환·초기 캐시·개발 작업이 포함된 첫날이므로 정상 일일 전송량으로 환산하지 않는다.
