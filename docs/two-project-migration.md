# Supabase 두 프로젝트 재구성

2026-09-22 사용자 승인: 기존 A를 대체하고, 같은 계정의 서로 다른 무료 조직 B·C에
프로젝트 하나씩 운영한다. 가격 이력과 분석을 유지한다. 이 문서는 이전 실행 기록과 전환 조건이며,
**아직 운영 연결을 바꾸거나 A를 중지·삭제하지 않았다.**

## 현재 준비 상태

- 기존 A: `ypmnadqnmadrburkrcka`, 계속 수집 중.
- 무료 조직 B `dnf-market-b` 생성 완료: `vefffbtbcaexgiydhlxu`.
- B 프로젝트 생성 양식: 이름 `dnf-market-b`, 서울, 새 테이블 Data API 자동 노출 해제.
  사용자 DB 비밀번호 입력·프로젝트 생성 대기. 비밀번호를 문서나 채팅에 넣지 않는다.
- C는 아직 생성하지 않는다. A+B가 활성 무료 프로젝트 두 개를 차지하기 때문이다.
- 운영 코드·GitHub Secrets·cron·기존 R2 manifest는 변경하지 않았다.

## 확인한 자료와 분배 초안

읽기 전용 조사: 2026-09-22 14:55 KST. `scripts/plan-db-split.ts`는 DB 내부에서
테이블별·아이템별 크기와 매물 조회 부담을 합산하고 작은 요약만 내려받는다.
전체 행 추출, API 수집, 빌드, DB 변경은 하지 않는다.

```powershell
node --env-file=.env --no-warnings scripts/plan-db-split.ts archive-work-split-20260922
```

출력 `archive-work-split-20260922/plan.json`은 gitignore된 로컬 조사 결과이며 배치 초안이다.
전환 도구나 수집기가 이 파일을 자동으로 적용하지 않는다.

| 초안 | 종목 수 | 관련 6개 테이블 논리 행 크기 | 매물 조회 JSON 하루 대리지표 |
|---|---:|---:|---:|
| B | 56 | 74.64 MB | 61.01 MB |
| C | 16 | 77.41 MB | 58.96 MB |

B에는 광휘·레전더리·레어 소울 결정, C에는 에픽·유니크 소울 결정과 닳아버린 순례의 증표가
배치된다. 개수를 절반으로 나누는 것보다 현재 부담이 비슷하다. 실제 요금·예상 고갈일을
이 수치로 계산하지 않는다. 행 크기는 인덱스·빈 공간을 제외하며, JSON 대리지표는
현재 매물 수와 폴링 주기가 하루 동안 일정하다는 가정이다. 프로토콜·빌드·보관 전송은 별도다.
종목 추가·삭제와 부하 변화 확인 후 아이템 ID별 배치를 고정한다. 폴링 주기의 자동 단축이
DB 소유자까지 바꾸게 해서는 안 된다.

## 보관본과 운영 복구의 차이

확인한 최근 성공 보관은 [Actions 35576485314](https://github.com/kimtaehoon1107-gif/dnf-price-tracker/actions/runs/35576485314).
소스 기준 2026-09-21 17:10:46 KST, 실제 복원 검증 17:14:22 KST.
1,061,877행, 압축 30,116,622바이트, `continuity=ok`, 연구 입력 재현 성공.
확인한 manifest: `manifests/ec4490cf8af646883749f8f6e9fdc7b07f5f1d0cf48e02464de5f76bf8ef1abb.json`.
이는 해당 실행 로그에서 확인한 기록이며 전환 시점의 최신 백업을 뜻하지 않는다.

R2는 운영에서 정리된 행도 남기는 연구 보관본이다. 그대로 운영 DB로 복원하면 삭제된 행이
되살아날 수 있다. `sourceHash`는 당시 운영 원본의 해시이고 보관 객체 자체의 행 집합과
다를 수 있으므로, 현재 운영 키·내용 대조 없이 이를 완전한 운영 스냅샷으로 취급하지 않는다.
보관 로더는 분석용 테이블만 만들며 운영 인덱스·기본값·시퀀스·함수·권한의 대체물이 아니다.

별도로 이전할 항목:

- 최근 변경·삭제를 포함한 실제 운영 행 집합, 열린 매물의 현재 수량·시각.
- `collection_runs`와 집계/수집 감시 상태. 보관의 `collection_quality`는 원본 로그가 아니다.
- `candle_pipeline_state.raw_from/raw_max_id`, 모든 시퀀스 다음 값, FK·인덱스·함수.
- pg_cron 10개 작업과 Vault의 GitHub dispatch 연결. 토큰은 비공개 경로로만 이전한다.
- 피드백 Edge Function, 비공개 관리자 설정·게시글 비밀번호 해시·제한 상태·함수 비밀값.
  현재 게시글 0개, 관리자 설정 1개다. Auth 사용자와 Storage 버킷은 각각 0개다.
- `web/feedback.js`의 API 주소와 `web/feedback.html`의 CSP 허용 주소.

## 두 DB 운영 구현 조건

1. 아이템의 items/trades/candles/listings/deltas/snapshots/runs를 같은 DB에 둔다.
   전역 이벤트·순위·레전더리 스캔·발행 예측·실측·피드백은 B가 소유한다.
2. 수집 Actions는 DB 소유자와 hot/rest를 구분한다. 같은 아이템을 두 DB에서 동시에
   수집하지 않는다. advisory lock은 DB 간에는 공유되지 않는다.
3. 사이트는 B·C의 아이템별 조회 결과를 합친 후 분석한다. 요일 평균·표준오차,
   Holm 보정·연구 바스켓·예측 학습·시장 TOP100은 전체 자료를 기준으로 계산한다.
   DB별로 계산한 최종 통계나 순위를 단순 연결하지 않는다.
4. 두 DB의 스냅샷은 원자적으로 같아지지 않는다. 공통 데이터 기준 시각과 각 DB의
   집계 완료 시각을 명시하고, 더 이른 완료 경계까지 분석한다. 한쪽 누락·지연·중복
   아이템 발견 시 배포를 중단하고 이전 정상 사이트를 유지한다.
5. R2 캐시 경로에 DB 식별자를 넣어 같은 SQL/날짜 결과가 서로 덮이지 않게 한다.
   원본 보관도 DB별 manifest/latest 경로를 분리하고 기존 A 보관본은 보존한다.
   `id`만 기본키인 테이블은 DB 사이에 충돌하므로 합칠 때 출처를 보존한다.
6. 집계·로컬 정리·상태 검사는 각 DB에 둔다. 정기 수집/사이트/event dispatch의 소유자를
   명시해 중복 호출을 피한다. C의 이상도 감시하고 운영 점검 도구가 두 DB를 검사한다.
7. B·C간 지속적인 원본 복제는 하지 않는다. 조회 결과를 빌드 작업에서 결합하고 R2를 재사용한다.

## 전환 순서와 중단 조건

1. 사용자 B 프로젝트 생성 및 비공개 연결 설정. 비밀번호를 URL로 조립할 때 percent-encode하고
   Session pooler + 인증서 검증을 사용한다. 처음에는 B 수집·예약 작업을 비활성 상태로 둔다.
2. B가 잠시 전체 72종을 담을 수 있는지 스키마·인덱스 포함 크기를 검증한다.
   500 MB 한도에 여유가 없으면 전체 임시 이전을 강행하지 않고 전환 순서를 재설계한다.
3. R2 자료를 재사용하되 현재 운영 행 집합과 맞춘 초기 자료를 준비한다.
   날짜별 변경 자료·운영 설정의 예상 추출량을 산정하고 A 남은 전송량보다 작을 때만 추출한다.
   대규모 추출을 반복하는 검증은 하지 않는다.
4. B에서 행 수·전체 내용 해시·자연키·원본/시간봉·시퀀스·권한·연구 결과를 대조한다.
   실제 PostgreSQL 17의 분할 전후 동등성 테스트를 운영 DB와 분리해서 수행한다.
5. 최종 전환은 진행 중인 수집/배포/보관과 cron 정리를 조정한 짧은 구간에서 수행한다.
   A의 마지막 변경·삭제를 반영하고 B 수집으로 넘긴다. 이후 자동 배포와 감시를 확인한다.
   전환 공백이 Neople 최근 100건 범위를 넘을 수 있으므로 소요 시간 상한과 실패 복귀를 먼저 검증한다.
6. B 정상 운영과 운영 설정 이전 확인 후 A를 일시중지한다. A를 먼저 삭제하지 않는다.
   B에 새 자료가 쌓인 뒤 단순히 A를 다시 켜면 기록이 갈라지므로 복귀도 변경 자료 대조가 필요하다.
7. C를 만들고 확정한 아이템 관련 자료를 옮긴다. B·C 결합 빌드와 보관을 검증한 뒤
   해당 아이템 수집 담당을 넘긴다. 검증되지 않은 B 원본 삭제는 하지 않는다.
8. 정상 정기 수집·사이트 배포·보관 실행과 누락 없는 이력을 확인한다.
   A 영구 삭제는 복원 가능한 최종 보관과 사용자 확인을 마친 마지막 작업이다.

현재 미완료: B 프로젝트 생성, 비공개 연결 설정, 운영용 복원·전환 도구,
두 DB 수집/빌드/연구/백업 구현과 통합 검증, 실제 이전, C 생성, A 중지·삭제.

공식 무료 한도는 Owner/Admin인 전체 조직 합산 활성 프로젝트 2개다.
조직마다 전송량 5 GB, 프로젝트마다 DB 500 MB이며, 삭제·재생성으로 기존 조직의 사용량이
초기화된다고 가정하지 않는다. 한도 초기화를 위해 조직을 반복 교체하는 운영 방식으로 설계하지 않는다.
