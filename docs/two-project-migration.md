### B 준비 도구

`scripts/setup-project-connection.ts`는 localhost 입력 화면에서 사용자가 입력한 비밀번호로
인증서를 검증하는 연결을 확인한 뒤 Git 제외 설정 파일에만 저장한다. 채팅·로그·커밋에
비밀번호나 전체 연결 문자열을 넣지 않는다. 기존 A 설정과 이미 저장된 B/C 설정을 덮어쓰지 않는다.

```powershell
# 생성한 빈 B 검사 후, 스키마와 아이템 설정만 준비 (이미 완료했으므로 재실행 불필요)
node --env-file=.env --no-warnings scripts/prepare-project-b.ts
node --env-file=.env --no-warnings scripts/prepare-project-b.ts --apply
```

대상 프로젝트 ID를 확인하고 비어 있는 DB에만 한 트랜잭션으로 적용한다. A는 읽기 전용
트랜잭션으로 접근하며, 설정 복사 전에 본문 크기 1MB 이하를 확인한다. 스키마 열 구성과
복사한 설정 전체를 대조하고 불일치하면 B 변경을 롤백한다. 운영 A의 열 순서는 과거 ALTER로
새 스키마와 다를 수 있어 이름/타입으로 대조하고, 행은 JSON 필드 이름으로 복사한다.

현재 복사한 아이템 설정은 **준비 시점의 사본**이다. 전환 직전 다시 동기화해야 한다.
열린 매물·최근 성공 수집 상태·전역 이벤트/예측/실측·피드백·감시/예약은 아직 이전하지 않았다.
B의 `candle_pipeline_state`는 새 DB 기본값이고 A의 원본 ID나 집계 성공 시각을 복사하지 않았다.
R2+신규 자료 통합이 완료되기 전에는 B의 `DATABASE_URL_B`를 운영 `DATABASE_URL`로 바꾸지 않는다.

R2는 운영에서 정리된 행도 남기는 연구 보관본이다. 그대로 운영 DB로 복원하면 삭제된 행이

보관 로더는 분석용 테이블만 만들며 운영 인덱스·기본값·시퀀스·함수·권한의 대체물이 아니다.

새 프로젝트에 필요한 초기 상태와 별도 이전 항목:

- 아이템별 현재 설정, 열린 매물의 현재 수량·시각, 필요한 재관측 무효화 상태.
  오래된 닫힌 매물·체결 전체는 복사하지 않는다.
- 수집 재시작에 필요한 최근 성공 기록과 별도 수집/집계 감시 상태.
  보관의 `collection_quality`는 원본 로그가 아니며 실패를 성공으로 재구성하면 안 된다.
- 신규 DB의 `candle_pipeline_state`와 시퀀스는 새 원본에 맞춘다. A의 `raw_max_id`를
  새 DB에 복사하지 않는다. 각 DB의 FK·인덱스·함수도 필요하다.
- pg_cron 10개 작업과 Vault의 GitHub dispatch 연결. 토큰은 비공개 경로로만 이전한다.
- 피드백 Edge Function, 비공개 관리자 설정·게시글 비밀번호 해시·제한 상태·함수 비밀값.
  현재 게시글 0개, 관리자 설정 1개다. Auth 사용자와 Storage 버킷은 각각 0개다.
- `web/feedback.js`의 API 주소와 `web/feedback.html`의 CSP 허용 주소.

## 두 DB 운영 구현 조건

1. 아이템의 새 items/trades/candles/listings/deltas/snapshots/runs를 같은 DB에 둔다.
   전역 이벤트·순위·레전더리 스캔·발행 예측·실측·피드백은 B가 소유한다.
2. 수집 Actions는 DB 소유자와 hot/rest를 구분한다. 같은 아이템을 두 DB에서 동시에
   수집하지 않는다. 전환 검증을 위한 짧은 겹침만 담당 시간표로 통제한다.
   advisory lock은 DB 간에는 공유되지 않는다.
3. 사이트는 고정한 R2 과거 자료와 B·C의 아이템별 조회 결과를 합친 후 분석한다. 요일 평균·표준오차,
   Holm 보정·연구 바스켓·예측 학습·시장 TOP100은 전체 자료를 기준으로 계산한다.
   DB별로 계산한 최종 통계나 순위를 단순 연결하지 않는다.
4. 두 DB의 스냅샷은 원자적으로 같아지지 않는다. 공통 데이터 기준 시각과 각 DB의
   집계 완료 시각을 명시하고, 더 이른 완료 경계까지 분석한다. 한쪽 누락·지연·중복
   아이템 발견 시 배포를 중단하고 이전 정상 사이트를 유지한다.
5. R2 캐시 경로에 DB 식별자를 넣어 같은 SQL/날짜 결과가 서로 덮이지 않게 한다.
   원본 보관도 DB별 manifest/latest 경로를 분리하고 기존 A 보관본은 보존한다.
   `id`만 기본키인 테이블은 DB 사이에 충돌하므로 합칠 때 출처를 보존한다.
6. 집계·로컬 정리·상태 검사는 각 DB에 둔다. 정기 수집/사이트/event dispatch의 소유자를
   명시해 중복 호출을 피한다. C의 이상도 감시하고 운영 점검 도구가 두 DB를 검사한다.
7. B·C간 지속적인 원본 복제는 하지 않는다. 조회 결과를 빌드 작업에서 결합하고 R2를 재사용한다.
8. 체결은 `(item_id,sold_date,unit_price,count,reinforce,dup_seq)`로 중복을 제거한다.
   동일 초·가격·수량의 별개 거래를 없애면 안 된다. 같은 자연키의 내용 충돌은 중단한다.
   관측 시각별 호가·잔량은 사전에 고정한 담당 출처 한 곳만 써서 겹침 수집의 가중치 왜곡을 막는다.
9. 전환 시간봉은 양쪽 시간봉을 더하지 않고 완전한 원본 구간을 합쳐 재집계한다.
   원본이 이미 불완전한 과거 봉을 재계산하면 안 된다. 담당 관측 공백, API 100건 포화,
   원본 완전성은 병합 성공만으로 증명되지 않으므로 별도 검증한다.
10. 매시간 전체 원본을 B·C에서 추출하는 빌드는 금지한다. 재사용할 R2 자료와 DB에서
    내려받을 결과의 범위를 먼저 정하고 전송 예산을 검증한다. 최종 보관도 변경 날짜 전체를
    읽을 수 있으므로 사전 용량 산정 없이 '작다'고 가정하지 않는다.

## 전환 순서와 중단 조건

1. 사용자 B 프로젝트 생성 및 비공개 연결 설정. 비밀번호를 URL로 조립할 때 percent-encode하고
   Session pooler + 인증서 검증을 사용한다. 처음에는 B 수집·예약 작업을 비활성 상태로 둔다.
2. 별도 PostgreSQL 17에서 과거 R2 자료+신규 DB 자료의 병합을 먼저 검증한다.
   체결 중복·동일키 복수 체결·ID 충돌·전환 시간봉·카드 단계·무매물 관측·연구 결과를 대조한다.
   실제 자료 전체 사이트 재현과 시간/전송 예산을 통과하기 전 수집은 A에 유지한다.
3. B에 스키마와 작은 초기 상태를 설치하고 원본 이력 전체를 복사하지 않는다.
   초기 상태와 A 최종 보관의 예상 추출량을 산정하고 남은 전송량보다 작을 때만 진행한다.
4. B에서 전체 72종 수집을 시작해 정상 성공을 확인하고, 아이템별 담당 전환 시각을 기록한다.
   짧은 겹침의 자연키 중복 제거를 확인한 뒤 A의 수집/집계/정리 예약과 진행 중 작업을 정리한다.
   수집 공백 상한과 실패 복귀를 먼저 검증한다. 생긴 공백을 '손실 없음'으로 추정하지 않는다.
5. A 마지막 보관을 생성해 복원 검증하고 immutable manifest를 전환 기록에 고정한다.
   피드백·전역 스캔·예측 발행·실측 확정·dispatch 등 운영 경로도 B로 넘긴다.
6. B 정상 운영, 최종 과거 보관과 운영 설정 이전 확인 후 A를 일시중지한다. A를 먼저 삭제하지 않는다.
   B에 새 자료가 쌓인 뒤 단순히 A를 다시 켜면 기록이 갈라지므로 복귀도 변경 자료 대조가 필요하다.
7. C를 만들고 확정한 아이템의 B 신규 자료·초기 상태를 옮긴다. R2+B·C 결합 빌드와 보관을 검증한 뒤
   해당 아이템 수집 담당을 넘긴다. 검증되지 않은 B 원본 삭제는 하지 않는다.
8. 정상 정기 수집·사이트 배포·보관 실행과 누락 없는 이력을 확인한다.
   A 영구 삭제는 복원 가능한 최종 보관과 사용자 확인을 마친 마지막 작업이다.
